# Release and submission checklist

Release preparation is current for **1.1.0** (October 31, 2026). Task Trellis is listed in the Community directory, marked as not manually reviewed by Obsidian staff; see [submission status](submission.md). From 1.0, releases keep the promises in [formats and compatibility](compatibility.md): a change that breaks them needs a major version. The preparation review on October 25 covered the official [developer policies](https://docs.obsidian.md/community-directory/developer-policies), [submission requirements](https://docs.obsidian.md/community-directory/submission-requirements-for-plugins), [plugin guidelines](https://docs.obsidian.md/Plugins/Releasing/Plugin%20guidelines), [manifest reference](https://docs.obsidian.md/Reference/Manifest), and [submission procedure](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin). Automated checks help prevent regressions; they do not imply acceptance by Obsidian.

Before a release or submission update:

- **Write the version's release notes.** Add `docs/releases/<version>.md` in the version-bump PR, following [the release-note guide](releases/README.md). Include user-visible changes, compatibility and actual validation. Release checks require this file and its matching heading; the publishing workflow uses it as the GitHub release description. Do not reuse an older version's test claims.

- **Disclose provenance accurately.** The MIT attribution above preserves the original license, but the directory has a separate fork policy. The two identified adapted implementations have been replaced and their historical notices retained. See [the provenance record](provenance.md). The maintainer chose to proceed without a separate eligibility inquiry; retain that history for directory review. The rewrite is not a guarantee of eligibility. No approval is recorded in this repository. The repository's GitHub `fork: false` flag alone does not settle this requirement.
- **Complete native compatibility testing.** Test on Obsidian 1.13.7 (the declared minimum for 0.1.10) and the current stable version, in a disposable vault. Check desktop light/dark themes, keyboard interaction, pop-out windows, reload/disable/re-enable with boards open, and task editing with and without Tasks, Daily notes, and Templater. Test iOS and Android, especially card movement and narrow layouts. No Node.js or Electron APIs are bundled. The maintainer has tested released builds in real iOS Obsidian. The shared renderer has also been tested in an iPhone simulator browser, including the software keyboard. These are distinct forms of evidence. See the [test report and remaining coverage](testing.md); full native compatibility checks across supported platforms remain necessary. Fix failures or adjust compatibility claims before release.
- **Review internal integrations.** Automatic board opening patches `WorkspaceLeaf.setViewState`; preserving board tabs uses the internal view registry with a public API fallback. Daily notes and tag search also use guarded internal interfaces. Smoke-test them after Obsidian updates; the declared API version alone cannot guarantee those interfaces.
- **Check the listing again.** The public repository has the required README, license and manifest. `task-trellis` / `Task Trellis` had no exact match in the public plugin catalog at review time; availability and naming still need confirmation when applying. There is no funding URL because the plugin does not request donations.
- **Prepare a release only when ready.** Keep `manifest.json`, `package.json`, `package-lock.json` and `versions.json` synchronized. Run `npm ci`, `npm run lint`, `npm test`, `npm run harness`, and `npm run package`. Inspect `dist/task-trellis/` and install those exact files in the test vault. The build checks mobile-incompatible runtime imports and preserves notices; packaging validates metadata and assets.
- **Publish and submit only with maintainer authorization.** A GitHub release must have a tag exactly matching the manifest version (for example `0.1.0`, without `v`) and attach `main.js`, `manifest.json` and `styles.css` as individual assets. The default branch must contain the matching manifest and reviewable source. Apply through the [Community directory](https://community.obsidian.md/) using an Obsidian account linked to GitHub. Address the automated review and any reviewer requests before publication. The package command and PR CI do not publish. Pushing a matching version tag triggers the release workflow, which checks, attests and publishes the install assets. Do not push a version tag until publication is authorized.
